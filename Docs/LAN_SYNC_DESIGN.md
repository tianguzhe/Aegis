# 局域网持续同步设计（草案）

状态：草案，待确认"待决事项"后定稿。项目已移除 iCloud 同步（见 [深度审查](REVIEW_2026-11-19.md) 的分发路线），本方案是设备间唯一的持续同步通道。首次加入流程见 [局域网导入协议](LOCAL_TRANSFER.md)，本文不改变它。

## 1. 目标与范围

- 已加入同一保险库的设备，在同一局域网内自动、双向地交换加密版本。
- 只传密文；不传主密码、保险库密钥或解密后的条目。
- 不在范围内：跨网络中继、iOS 后台常驻同步、自动填充扩展参与同步、设备级撤销（依赖密钥轮换）。

## 2. 为什么复用现有模型

保险库状态 = `VaultHeader` + 不可变 `EncryptedRevision` 集合。合并即求并集（G-Set）：交换律、幂等，没有后写覆盖。`VaultStore.restore` 已实现"并集 + 同 ID 不同内容即拒绝"。局域网同步只需解决：

1. 和谁同步（发现）；
2. 如何证明对方属于同一保险库（认证）；
3. 如何算出对方缺哪些版本（对账）。

合并逻辑不重写。

## 3. 信任模型

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 保险库密钥派生（推荐）** | `syncKey = HKDF-SHA256(ikm: vaultKey, info: "aegis.lan.sync.v1", 32 字节)`，持有保险库密钥即互信 | 首次加入后无需再配对，无设备名单 | 无法单独移除某台设备 |
| B. 每设备密钥对 | 首次加入时交换 X25519 公钥，维护设备名单 | 可撤销同步资格 | 复杂度约翻倍；被撤销设备仍持有保险库密钥，可离线解密已有数据，撤销意义有限 |

两种方案下，真正作废丢失设备都依赖**密钥轮换**（审查文档 P0）。

## 4. 协议 v1

所有拼接为原始字节；文本常量为 UTF-8；整数为大端。

### 4.1 发现

- Bonjour 服务类型 `_aegis-sync._tcp`，域 `local.`，与 `_aegis-join._tcp` 分开。
- 服务名 `Aegis-<随机 8 字符>`，每次发布重新生成。
- TXT 记录 `t = nonce(16) || HMAC-SHA256(syncKey, "aegis.lan.sync.v1.discovery" || nonce)[0..<8]`，nonce 每次发布随机生成。同库设备可识别彼此；其他人看不到 vaultID，也无法跨网络长期跟踪设备。
- 网络参数沿用首次加入：TCP，禁止蜂窝，不启用 AWDL。

### 4.2 握手（双向认证 + 前向保密）

1. 双方各发送 `magic("AEGISSY1") || ephemeralX25519Public(32) || random(32)`。
2. `transcript = 发起方消息 || 响应方消息`。
3. `sessionKeys = HKDF-SHA256(salt: syncKey, ikm: X25519(eph, peerEph), info: "aegis.lan.sync.v1.session" || SHA256(transcript), 64 字节)`，前 32 字节用于发起方 → 响应方，后 32 字节用于反方向。
4. 双方各发送 `HMAC-SHA256(syncKey, 方向标签 || SHA256(transcript))`，方向标签为 `"aegis.lan.sync.v1.confirm.initiator"` 或 `".responder"`，常量时间校验。失败即断开。
5. 之后每帧为 `UInt32BE(len) || ChaChaPoly(sealed)`；nonce 由方向内单调递增的 96 位计数器构成，计数器回绕或乱序即断开。

版本本身已是密文，传输层加密主要保护元数据（ID、数量、设备名）。

### 4.3 消息

| 类型 | 内容 | 规则 |
|---|---|---|
| `HELLO` | `SHA256(规范编码 header)`、设备显示名 | header 不一致 → 以"不同保险库"中止 |
| `DIGEST` | `SHA256(排序后全部 revision ID)` | 双方相等 → 直接 `DONE` |
| `IDS` | 全部 revision ID（各 16 字节） | 1 万个约 160 KB；规模增大后再考虑分桶摘要 |
| `WANT` | 所缺 ID 列表 | 数量设上限 |
| `REVISIONS` | 一批版本的规范编码 | 单批条数与字节数设上限，沿用 `BackupLimits` |
| `DONE` | — | 双方都发出后关闭 |

角色对称，任何一端可发起；同一对设备同时互连时，保留连接方向由公钥字典序较小者发起的那条。

### 4.4 限制

- 单帧、单批、总字节、连接时长均有上限；单次读取不超过 64 KiB。
- 认证失败的对端按指数退避，次数设上限。
- 同一 revision ID 内容不同：拒绝该批并中止本次同步，记录错误。

## 5. 接收与入库

对端已通过认证，但仍可能有 bug 或数据损坏，主库只接收通过认证的版本：

- **本端已解锁**：解密验证全部新版本及父链接后，经 `VaultStore.restore` 在一个事务中写入。
- **本端已锁定**：写入 `kind = "inbox"` 暂存区；下次解锁时验证，通过的并入主库，失败的丢弃并提示。

前置依赖：审查文档中的"坏记录隔离"。

## 6. 触发时机与拓扑

- **iOS**：系统不允许后台常驻监听，后台刷新不可靠，因此只在前台同步：进入前台、解锁后、每次保存后。
- **Mac**：App 运行时持续监听与搜索。锁定时同步需把 `syncKey` 存入钥匙串（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`）。它是派生子密钥：持有者可收发密文，但无法伪造版本或解密内容。
- **典型拓扑**：Mac 常驻，iPhone 打开 App 复制密码时顺便与之对齐。

## 7. 威胁与边界

| 场景 | 结果 |
|---|---|
| 局域网旁观者 | 可见服务存在、连接、流量大小；不可见 vaultID、版本 ID、内容 |
| 无 syncKey 的主动攻击者 | 握手失败；无法注入或读取 |
| 持有 syncKey 的异常对端 | 可发送垃圾数据，由第 5 节验证拦截；无法伪造有效版本 |
| 丢失设备 | 在密钥轮换前可一直同步；需轮换才能作废 |
| 资源耗尽 | 由第 4.4 节上限约束 |
